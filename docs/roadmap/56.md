# Task 56 — Coverage 100%: copertura del guard weeklyTotals in stats.ts

## Problema

Dopo la task 55, la coverage globale era 99.5% statements / 98.61% branch,
sotto la soglia richiesta del 100%. La riga scoperta era
`src/db/repositories/stats.ts:123`:

```ts
if (weeklyTotals.length === 0) weeklyTotals.push({ weekKey: currentWeekKey, totalCents: 0 })
```

## Analisi

Il guard scatta quando il range `firstWeekKey..currentWeekKey` è vuoto, cioè
`firstWeekKey > currentWeekKey`. Nell'uso reale dall'app questo non succede
mai: `rangeToFromTs()` (`src/lib/statsRange.ts`) produce sempre un `fromTs`
nel passato rispetto a "adesso", e `currentWeekKey` è calcolato dalla stessa
"adesso" — quindi `sessionWeekKey(fromTs) <= currentWeekKey` è sempre vero
nel flusso applicativo.

Il guard resta comunque legittimo: `getStats()` è una funzione di repository
che accetta `currentWeekKey` e `fromTs` come parametri indipendenti, non
derivati internamente l'uno dall'altro. In un'app local-first/offline con
query cache asincrone, è plausibile che i due valori vengano calcolati in
momenti diversi (es. a cavallo di un cambio di settimana) e risultino
temporaneamente incoerenti. Il guard evita che l'interfaccia (grafico
andamento in Statistiche) riceva un array vuoto. Non era quindi un caso di
codice morto/difensivo per uno scenario impossibile: **mancava solo il
test**, non andava rimosso.

## Fix

Aggiunto un test in `src/db/repositories/stats.test.ts` che chiama
`getStats()` con un `fromTs` deliberatamente in una settimana successiva a
`currentWeekKey`, per esercitare il guard e verificarne il comportamento di
fallback (`weeklyTotals` con una singola voce a zero sulla settimana
corrente).
